
## web (client portal + back-office)

Interpretations made while building `web/` from SPEC.md. Backend authors: the items marked **(API expectation)** are what the web assumes; the UI tolerates the listed alternatives.

1. **OTP sign-up flow.** The web calls `POST /api/auth/otp/verify` with `role: "CLIENT"` and no `acceptTerms` first. If the answer is `TERMS_REQUIRED` (or `AUTH_ROLE_REQUIRED`) the user is new: the UI shows the Terms + Privacy checkbox and re-sends the **same code** with `acceptTerms: true`, `termsVersion`, `privacyVersion` (versions read from `GET /api/public/legal/terms|privacy`). **(API expectation)** the backend checks role/terms *before* marking the OTP as used, and these two errors do not count as wrong attempts. For an existing user `role` is ignored.
2. **Non-client accounts.** If verify returns a user whose role is not `CLIENT`, the web does not keep the token and points the person to the engineer app at `/m/`.
3. **Two contract documents.** The client can accept only the `CLIENT_SERVICES` document (`POST /api/client/contracts/{id}/documents/{docId}/accept`); `ENGINEER_DELIVERABLES` is shown read-only with "awaiting the engineer" until the engineer accepts it in h5.
4. **Contract detail shape (API expectation).** `GET /api/client/contracts/{id}` includes `documents[]`, `milestones[]` (with `clientAmountUsd`, `status`, `submittedNote`, `disputeReason`) and, since the spec has no attachment list endpoint, `attachments[]` `{id, filename, sizeBytes, milestoneId}` (milestones may also carry `attachments[]`). Optional extras used when present: `projectTitle`, `engineerAlias`. Messages use `senderUserId` (compared with `/api/me` id) and optional `senderAlias`.
5. **Hire response.** `POST /api/client/applications/{id}/hire` may return the contract (`id`) or `{contractId}`; the web navigates to `/client/contracts/{contractId ?? id}`.
6. **Fake checkout return.** `GET /api/payments/{id}` has no contract id in the spec; the web remembers `paymentId → contractId` in `sessionStorage` before leaving for checkout and also accepts an optional `contractId` in the payment response. After confirm it goes to `/client/contracts/{id}?paid=1`. Same-origin checkout URLs are opened with the router; other URLs (Stripe) with `window.location`.
7. **Project flags shape.** `flags` may be an array of strings, an array of objects (`keyword`/`term`) or an object of arrays; the UI flattens it to keywords. The project form also shows a *non-blocking* live hint using the SPEC §1 keyword lists; the backend remains authoritative.
8. **Project edit + submit.** Edit sends `PUT /api/client/projects/{id}` with the same body as create minus `submit`; "Submit for review" then calls `POST /api/client/projects/{id}/submit`. Milestones are sent without ids (full replacement). Drafts are only validated client-side for a title; submit validates everything (sum = budget, end date, ≤ 12 months, due dates within range, 4 declarations).
9. **Validation field paths.** `data.fields` keys like `milestones[0].amountUsd` are normalised to `milestones.0.amountUsd`. Field codes are translated when known (`REQUIRED`, Bean Validation names such as `NotBlank`, `Positive`, `Size`, …) and shown raw otherwise. Business codes are attached to fields: `PROHIBITED_CATEGORY`→category, `MILESTONE_SUM_MISMATCH`/`MILESTONES_REQUIRED`→milestones, `END_DATE_REQUIRED`/`DURATION_TOO_LONG`→end date, `DECLARATIONS_REQUIRED`→declarations.
10. **Error codes not in the spec.** The web also translates `NETWORK_ERROR`, `INTERNAL_ERROR`, `UNKNOWN_ERROR`, `CONFLICT`, `INVALID_STATE`, `INVALID_STATUS`, `INVALID_CREDENTIALS`, `ACCOUNT_LOCKED`, `ADMIN_LOCKED`, `TOTP_REQUIRED`, `TOTP_INVALID`, `SANCTIONS_NOT_CLEAR`, `PARTNER_REF_REQUIRED`, `CATEGORY_NOT_ALLOWED`, `FILE_TOO_LARGE`, `UNSUPPORTED_FILE_TYPE`, `PAYMENT_PROVIDER_NOT_FAKE`, `PAYMENT_ALREADY_PAID`, `CONTRACT_NOT_ACTIVE`, `ACCOUNT_DELETED`. Any other code falls back to `message`.
11. **Lists.** Every list endpoint is accepted either as a plain array or as a page `{records,total,page,size}`. Admin tables send `page`/`size`.
12. **Admin menu by role** (SUPERADMIN sees everything): Companies = OPS, COMPLIANCE; Engineers, Projects, Disputes = OPS; Settlements = FINANCE; Compliance and Categories = COMPLIANCE; Mail outbox = OPS, COMPLIANCE (role not given in the spec); Admins = SUPERADMIN only. Direct navigation to a forbidden section redirects to the dashboard with a notice.
13. **Admin reviews.** Company approve is disabled unless the sanctions result chosen is `CLEAR`; reject requires a note. Engineer approve is disabled until a `partnerRef` is entered. Project "request changes" and "reject" require a note. Dispute resolution requires a note.
14. **Admin category list.** `GET /api/admin/categories` may use `{nameEn,nameEs,nameZh}` or the public `{name:{en,es,zh}}` shape.
15. **Downloads** (settlement CSV, attachments, `GET /api/me/export`) use an authenticated `fetch` and save the blob, taking the filename from `Content-Disposition`.
16. **Company sizes** are free strings in the spec; the web offers `1-10`, `11-50`, `51-200`, `201-1000`, `1000+`. Country is an ISO-2 select (names from `Intl.DisplayNames`, no network). The company form is editable only in `DRAFT` / `REJECTED`; "Submit for review" saves the company (`PUT`) then posts the declarations with the version returned by `GET /api/public/legal/client-declarations`.
17. **Locales.** Client area: browser language if `en`/`es`, else `en`; stored in `localStorage['qiao.locale']` and, when logged in, saved with `PUT /api/me`. Admin area: `es` by default, stored separately in `localStorage['qiao.admin.locale']`.

## h5 (engineer mobile app)

Interpretations made while building `h5/` from SPEC.md. Items marked **(API expectation)** are what the h5 assumes; the UI tolerates the listed alternatives.

1. **OTP sign-up flow** (same expectation as web #1). The login page always shows the agreement block (we cannot know beforehand whether the email is new): Terms+Privacy checkbox and a separate, optional `CROSS_BORDER_PROCESSING` checkbox, both unticked. Verify always sends `role: "ENGINEER"` and `locale`; `acceptTerms: true` + `termsVersion` + `privacyVersion` (from `GET /api/public/legal/terms|privacy`) only when the box is ticked. On `TERMS_REQUIRED` / `AUTH_ROLE_REQUIRED` the UI asks the person to tick it and re-sends the **same code**. **(API expectation)** these two errors do not consume the OTP nor count as wrong attempts.
2. **Cross-border consent at registration** is recorded right after a successful verify with `POST /api/me/consents {type: CROSS_BORDER_PROCESSING, granted: true}`, only if ticked and `GET /api/me` does not already show it. It is optional for registering/browsing; the profile page asks for it before "submit for review" (backend still enforces `CONSENT_REQUIRED`).
3. **Non-engineer accounts.** If verify or `/api/me` returns a role other than `ENGINEER`, the h5 drops the token and tells the person to use the client website.
4. **Region** is stored as the English name of a mainland province-level division (`Beijing`, `Guangdong`, `Inner Mongolia`, … 31 values) so the client portal can show it in en/es without a lookup table; the h5 shows the Chinese name. Unknown stored values are shown as-is.
5. **Profile.** `GET /api/engineer/profile` may return `null` or 404 for a new engineer (empty draft). The form is read-only while `PENDING_REVIEW`. "Submit" = `PUT /api/engineer/profile` then `POST /api/engineer/profile/submit`. Client-side checks before submitting: headline, ≥1 skill, region, declaration ticked, cross-border consent. Number fields are sent as numbers or `null`; `portfolioLinks` without empty entries.
6. **Contract documents.** The engineer accepts only `ENGINEER_DELIVERABLES`; a `CLIENT_SERVICES` document, if returned, is shown read-only with its acceptance status. **(API expectation)** documents carry `id, kind, templateVersion, body, sha256, acceptedAt`.
7. **Contract detail / list shape (API expectation).** `GET /api/engineer/contracts/{id}` → `{id, projectId, projectTitle?, status, talentTotalUsd, activatedAt?, documents[], milestones[]}`; milestones `{id, seq, title, deliverable, dueDate, talentAmountUsd, status, submittedNote?, submittedAt?, acceptedAt?, disputeReason?}`. The spec stores no revision reason column: for `REVISION_REQUESTED` the h5 shows `revisionReason` if present, else `disputeReason`. The contract list may include `milestones[]` (used for the progress bar) and `projectTitle`.
8. **Delivery.** Files are uploaded as soon as they are picked (`POST /api/contracts/{id}/attachments`, multipart `file` + `milestoneId`, 20 MB checked client-side too); the returned ids go to `POST /api/engineer/milestones/{id}/submit {note, attachmentIds}`. Submit is offered only when the contract is `ACTIVE` and the milestone is `FUNDED` or `REVISION_REQUESTED`.
9. **Messages.** `GET /api/contracts/{id}/messages?page=1&size=100` (array or page accepted), sorted by `createdAt` then `id`; own messages are those whose `senderUserId` equals `/api/me` `id`. Polled every 20 s while the page is visible.
10. **Applications / CV consent.** `GET /api/engineer/applications` items are read as `{id, projectId, projectTitle, status, coverNote?, talentTotalUsd?, createdAt?}`. Whether `SHARE_FULL_CV` was granted for a project comes from `GET /api/me/consents` (`type=SHARE_FULL_CV`, `scopeRef` = projectId compared as string). The grant prompt is shown for `SELECTED`; withdrawal is possible from "我的 → 隐私与授权".
11. **Consents list (API expectation).** `GET /api/me/consents` items `{type, granted, version, scopeRef, createdAt}`. `POST /api/me/consents` sends `scopeRef` as a string. `TERMS`/`PRIVACY` are shown as non-withdrawable (deleting the account is the way out); the others have toggles with a confirmation that explains the consequence (withdrawing `SHARE_PROFILE_PSEUDONYMIZED` = you do not appear in new applications and cannot send new ones).
12. **Applying.** Before `POST /api/engineer/projects/{id}/applications` the h5 checks `/api/me` `consents.SHARE_PROFILE_PSEUDONYMIZED`; if missing (or the API answers `CONSENT_REQUIRED`) it shows a sheet listing exactly what clients see (alias, headline, skills, years, region, languages, rate, availability, rating, cover note and prices) and what they never see, records the consent and then applies. Prices are prefilled with each milestone's `talentAmountUsd` and sent rounded to cents.
13. **Markdown.** Legal texts and contract documents are rendered with a small strict renderer (`h5/src/utils/markdown.ts`), not markdown-it: markdown-it's linkify code puts `http://` strings in the bundle, which the zero-external-URL check forbids. Raw HTML is escaped, images are shown as alt text (no fetch), links only relative / `#` / `http(s)` / `mailto`.
14. **Zero external URLs in the build.** Vant 4.10's icon font is inlined as woff2 but keeps a `//at.alicdn.com/...woff` fallback; a Vite plugin removes that fallback, and also the scheme of Vue's production error-info string `https://vuejs.org/error-reference/`. `scripts/check-no-external.mjs` also flags protocol-relative URLs in HTML/CSS and `ws(s)://`; the only allowed URLs are `http://www.w3.org/...` namespaces.
15. **Locale.** Default `zh-CN`, stored in `localStorage['qiao.h5.locale']`, sent as `Accept-Language` and in OTP request/verify; when changed while logged in it is saved with `PUT /api/me {locale}`. Legal docs are requested with `?locale=zh-CN|en`.
16. **Errors.** Every spec code has zh-CN and en text; the h5 also handles `NETWORK_ERROR`, `SERVER_ERROR` (5xx without envelope), `FILE_TOO_LARGE` (413) and, like the web, `INTERNAL_ERROR`, `UNKNOWN_ERROR`, `CONFLICT`, `INVALID_STATE`, `INVALID_STATUS`, `CONTRACT_NOT_ACTIVE`, `UNSUPPORTED_FILE_TYPE`, `ACCOUNT_LOCKED`, `ACCOUNT_DELETED`. Unknown codes show a generic text with the code (the English `message` when the UI is in English). `VALIDATION_ERROR` lists the translated field names from `data.fields`.
17. **Landing page** is static (no API call): the prohibited categories and their reasons come from SPEC §9 in the i18n files, so the page renders even if the backend is down. Filters on the project list use `/api/public/categories` (allowed ones) with the SPEC list as fallback.
18. **Money and dates.** Amounts are USD as returned (engineers see talent amounts only), with a note that the partner pays RMB at the period rate with tax withheld. Dates are shown as `YYYY-MM-DD`. Earnings totals (accepted / paid / pending) are computed client-side from `GET /api/engineer/earnings`.

## backend

Interpretations and deviations in `backend/`. Items 1–12 align the API with the web and h5 sections above.

1. **OTP verify.** The code is checked first (wrong code → attempt counted, `OTP_INVALID`; 5th wrong → `OTP_LOCKED`, 15 min). For a new email the backend then requires `role` (`AUTH_ROLE_REQUIRED`) and `acceptTerms=true` (`TERMS_REQUIRED`) **before** consuming the code; these two errors never count as attempts, so the same code can be re-sent. For existing users `role` is ignored. `termsVersion`/`privacyVersion` are recorded as sent (current version when omitted). Locks: on `app_user.otp_locked_until` for registered users, derived from the exhausted `otp_code` row for unknown emails; requesting a new code while locked also answers `OTP_LOCKED`.
2. **Validation field codes.** `data.fields` values are the Bean Validation constraint names (`NotBlank`, `NotNull`, `Size`, `Email`, `Pattern`, `DecimalMin`, `Digits`, `Min`, `Max`, …); service checks use `REQUIRED`, `INVALID`, `END_BEFORE_START` (project `endDate`) and `DUE_OUTSIDE_RANGE` (`milestones[i].dueDate`). Malformed JSON / bad enum or type → `INVALID` on the field path.
3. **Error codes beyond the spec** (HTTP status): `INVALID_STATE` 409 (illegal transition), `INTERNAL_ERROR` 500, `METHOD_NOT_ALLOWED` 405, `UNSUPPORTED_MEDIA_TYPE` 415, `ACCOUNT_DISABLED` 403, `INVALID_CREDENTIALS` 401, `ADMIN_LOCKED` 429, `TOTP_REQUIRED` 401, `TOTP_INVALID` 401, `EMAIL_TAKEN` 409, `SANCTIONS_NOT_CLEAR` 400, `PARTNER_REF_REQUIRED` 400, `CATEGORY_NOT_ALLOWED` 409 (admin approves a project whose category was disallowed after submission; on create/update the spec's `PROHIBITED_CATEGORY` 400 is used), `PROJECT_NOT_OPEN` 409, `CONTRACT_NOT_ACTIVE` 409, `FILE_TOO_LARGE` **413** (JSON envelope; multipart limit is 21 MB and the service enforces 20 MB), `UNSUPPORTED_FILE_TYPE` 400, `PAYMENT_PROVIDER_NOT_FAKE` 409, `PAYMENT_ALREADY_PAID` 409 (confirming twice, or checkout of a milestone already funded), `PAYMENT_PROVIDER_ERROR` 502, `INVALID_SIGNATURE` 400 (Stripe webhook), `TRANSFER_LIMIT_REACHED` 409. Spec codes keep their meaning: `CONSENT_REQUIRED`, `PROFILE_NOT_APPROVED`, `ALREADY_APPLIED`, `COMPANY_NOT_APPROVED`, `MILESTONE_NOT_FUNDED`, `NOTHING_TO_SETTLE`, `ACCOUNT_HAS_ACTIVE_CONTRACTS` are 409; `CV_CONSENT_REQUIRED` is 403; the project-rule codes are 400; `OTP_LOCKED` and `RATE_LIMITED` are 429. `CONSENT_REQUIRED` carries `data.consentType`.
4. **Ownership.** Resources that exist but do not belong to the caller answer `404 NOT_FOUND` (no existence leak). Role mismatches on a path prefix answer 403.
5. **Pagination.** Paged (`{records,total,page,size}`): `GET /api/engineer/projects`, `/api/admin/companies`, `/api/admin/engineers`, `/api/admin/projects`, `/api/admin/audit`, `/api/admin/outbox`. Everything else returns a plain array. `GET /api/contracts/{id}/messages` returns the whole thread oldest first; `page`/`size` are accepted and ignored.
6. **Project flags** are `[{type: "EMPLOYMENT"|"SENSITIVE", keyword}]`, computed on create/update from title, description, skills and milestone texts. Latin keywords match on word boundaries (optional plural `s`/`es`), Chinese keywords as substrings. Messages with any hit get `flagged=true`.
7. **Contract views.** Detail (`GET /api/client|engineer/contracts/{id}`, also returned by hire and by document accept): `{id, projectId, projectTitle, status, engineerAlias, clientTotalUsd | (clientCountry, talentTotalUsd), clientAcceptedAt, engineerAcceptedAt, activatedAt, completedAt, createdAt, documents[], milestones[], attachments[]}`. `documents` holds **both** documents for both parties (`{id, kind, templateVersion, locale, body, sha256, accepted, acceptedByUserId, acceptedAt}`); each party can only accept its own kind (`CLIENT_SERVICES` client, `ENGINEER_DELIVERABLES` engineer; the other kind → 404). Client milestones carry `clientAmountUsd`, engineer milestones `talentAmountUsd`, both `status, submittedNote, submittedAt, acceptedAt, revisionReason, disputeReason`. `attachments[]` = `{id, milestoneId, uploaderUserId, filename, contentType, sizeBytes, createdAt}`. List items have the same shape with `milestones[]` but `documents`/`attachments` null. Accepting an already accepted document is a no-op.
8. **`revision_reason`** column added to `contract_milestone` in `V1__init.sql` (nothing released yet), exposed as `revisionReason`; `POST /api/client/milestones/{id}/request-revision {reason}` stores it.
9. **Messages** `{id, contractId, senderUserId, senderSide: CLIENT|ENGINEER, senderAlias, body, flagged, createdAt}`; `senderAlias` is the engineer alias or the company name.
10. **Payments.** `GET /api/payments/{id}` and the fake confirm return `{id, contractId, contractMilestoneId, provider, status, amountUsd, paidAt}`. Stripe: `checkout.session.completed` / `async_payment_succeeded` with `payment_status=paid` mark the payment PAID; cancel URL = contract page; a dispute resolved as `REFUND` refunds through the Stripe API (fake: no-op). `PAYMENT_PROVIDER=stripe` without `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` fails at startup.
11. **Admin categories** `GET/PUT /api/admin/categories` use `{code, nameEn, nameEs, nameZh, allowed, sort}`; the public list keeps `{code, name:{en,es,zh}, allowed}` (all categories, prohibited ones with `allowed=false`).
12. **Admin roles.** SUPERADMIN implies OPS, FINANCE and COMPLIANCE. Mail outbox: OPS, COMPLIANCE (+SUPERADMIN). Admins list/create: SUPERADMIN. Dashboard: any admin. Admin engineer endpoints use the **profile id**; the view is `{id, userId, email, partnerRef, profile:{…full profile…}, createdAt, updatedAt}`. TOTP is verified when `admin_user.totp_secret` (base32) is set; there is no enrolment endpoint in phase 1.
13. **Onboarding records.** Registration creates the per-role record: engineer profile (DRAFT, alias `QE-XXXX`) or client company (DRAFT, empty name) with its single `client_member`. `GET /api/engineer/profile` therefore always returns the profile (never 404/null); `GET /api/client/company` always returns the company.
14. **Company.** `PUT` only in DRAFT/REJECTED (REJECTED → DRAFT); declarations require name and country and `version` = current `client-declarations` version (else `VALIDATION_ERROR` on `version`); the stored hash is the SHA-256 of the text in the user's locale. Review: PENDING_REVIEW + APPROVE(CLEAR) → APPROVED, + REJECT → REJECTED; APPROVED + REJECT with `HIT` → BLOCKED (its DRAFT/SUBMITTED/CHANGES_REQUESTED/OPEN projects are cancelled); APPROVED + APPROVE(CLEAR) records a re-screening. `size` is free text (web offers `1-10`, `11-50`, `51-200`, `201-1000`, `1000+`).
15. **Engineer profile.** `PUT` allowed in DRAFT, REJECTED (→ DRAFT) and APPROVED (stays APPROVED); refused (`INVALID_STATE`) while PENDING_REVIEW. Submit requires headline, ≥1 skill, years, region and English level (`VALIDATION_ERROR`), the declaration (`DECLARATIONS_REQUIRED`) and `CROSS_BORDER_PROCESSING` (`CONSENT_REQUIRED`). Region is free text (≤ 64 chars). Pseudonymized profile = `{alias, headline, skills, yearsExperience, region, englishLevel, spanishLevel, hourlyRateUsd, availabilityHoursWeek, ratingAvg, ratingCount}`.
16. **Projects.** Structural rules (category, end date, ≤ 12 months, ≥ 1 milestone, due dates inside the period, milestone sum = budget) apply to drafts too because the columns are mandatory; the four declarations are only required when submitting. `PUT` (DRAFT/CHANGES_REQUESTED) replaces the milestones; `submit:true` in the body submits. Added `POST /api/client/projects/{id}/cancel` (DRAFT/SUBMITTED/CHANGES_REQUESTED/OPEN → CANCELLED, active applications DECLINED) for the cancel transition in §10. Engineers see a project when OPEN or when they applied to it. Client project views include `applicationCount`.
17. **Applications.** `select` is allowed from SUBMITTED or SHORTLISTED; hire only from SELECTED on an OPEN project. WITHDRAWN applications are hidden from the client and cannot be re-submitted (unique project+engineer → `ALREADY_APPLIED`). Prices must cover every project milestone exactly once (`VALIDATION_ERROR` on `prices`). Client prices are `{milestoneId, talentAmountUsd, clientAmountUsd}`. Shortlist/select/decline responses also count as a pseudonymized-profile transfer.
18. **Transfers.** One `transfer_event` row per engineer per disclosure. When a disclosure would take the year's unique-engineer count above 100 000, data of not-yet-counted engineers is refused with `TRANSFER_LIMIT_REACHED`.
19. **Contracts.** Templates exist in `en` and `zh-CN`; Spanish-speaking clients receive the English `CLIENT_SERVICES`. The legal entity names come from `APP_CONTRACTS_HK_ENTITY_NAME` / `APP_CONTRACTS_PARTNER_ENTITY_NAME`. Fee pct and amounts are fixed at hire time (client price = talent × (1 + fee)).
20. **Settlements.** A batch takes every ACCEPTED milestone with a PAID payment and no line yet; `period` (`YYYY-MM`) is a label, not a date filter. The CSV is UTF-8 with BOM, CRLF, and cells starting with `= + - @` prefixed with `'`. The partner API never sees DRAFT batches; lines can be paid only while the batch is EXPORTED; line views add `partnerPaymentRef, iitWithheldCny, netPaidCny, paidAt`. Earnings list milestones of ACTIVE/COMPLETED contracts.
21. **Account deletion.** Refused while any contract (as engineer or company member) is ACTIVE. Otherwise: email → `deleted-{id}@deleted.invalid`, status DELETED, current token revoked (other tokens stop working because the account is no longer ACTIVE), engineer profile free texts wiped (alias/partnerRef kept for settlements), applications withdrawn and cover notes cleared, the client's non-contracted projects cancelled, contracts pending signatures TERMINATED. Contracts, payments, settlements, messages, files, consents and audit rows are kept. `GET /api/me/export` returns the envelope with `Content-Disposition: attachment`.
22. **Dashboard** `{companies:{byStatus}, engineers:{byStatus}, projects:{byStatus}, contracts:{byStatus}, gmvUsd, feesUsd, transfers:{year, uniqueEngineers, level}}`; GMV = PAID (not refunded) payments, fees = GMV − talent amounts of those milestones.
23. **Mail.** `MAIL_MODE=smtp` sends after the transaction commits and logs SENT/FAILED in `mail_outbox`; OTP bodies are stored as `[redacted]` in that mode. The backend also mails review outcomes, hire, milestone funded/submitted/accepted/revision (en/es/zh-CN).
24. **Uploads.** Any file type except executables (PE, ELF, Mach-O, shebang scripts); the content type is sniffed from the bytes (unknown binaries → `application/octet-stream`), names are sanitized, files are stored under random keys and always served with `Content-Disposition: attachment`.
25. **Infrastructure.** Rate limits (OTP 1/min per email and 20/h per IP, admin login 10/min per IP) are in-memory: fine for one instance, move to Redis before scaling out. `/api/dev/last-otp` keeps codes in memory (dev/test profiles only). All timestamps are UTC; the JDBC URL must include `connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true`. The `review` table exists (P1) without endpoints. Legal texts and contract templates are marked as drafts pending legal review; all legal versions start at `2026-11-01`.

## security review

Independent review of `backend/` (access control, authentication, payments, partner API, files, data exposure, injection). Each fix has a regression test that fails on the reviewed commit (`942eefd`); tests are in `AuthIT`, `AdminAuthIT`, `ContractLifecycleIT`, `SecurityReviewIT`, `ProductionProfileIT` and `ProductionSafetyCheckTest`.

1. **OTP attempt budget is per email, not per code.** Requesting a new code used to reset the 5-attempt counter, so an attacker could make 4 guesses per code forever without ever triggering the lock. A new code now inherits the failed attempts of the code it replaces while that code is younger than the lock duration (15 min). Only the email's most recent code can be used: an older, still unexpired code no longer becomes valid again after a newer one is used.
2. **OTP and admin-login attempts are counted under a row lock.** The attempt counter was read before and incremented after the comparison, so parallel requests all passed the limit check (on the reviewed code 12 of 15 parallel OTP guesses were compared, and all 12 parallel admin password guesses were checked). `OtpService.check` and `AdminAuthService.login` now run each attempt in a short transaction that locks the `otp_code` / `admin_user` row (`FOR UPDATE`), and throw only after it commits, so failures still persist.
3. **OTP codes are redacted from the mail outbox subject too.** The OTP subject (`Your Qiao sign-in code: 123456`) was stored in `mail_outbox` with `MAIL_MODE=smtp`, where OPS/COMPLIANCE admins read it via `GET /api/admin/outbox` and could sign in as any user; it was also written to the logs. With SMTP both subject and body of sensitive mails are stored as `[redacted]`, and sensitive subjects are never logged. `MAIL_MODE=log` still stores the code in the outbox, because there the outbox is the mailbox (dev/e2e only).
4. **Engineers no longer see the client company name in contract messages.** `MessageView.senderAlias` of client messages is now `null` for the engineer (still the company name for the client side). This supersedes backend item 9; the field is kept and h5 does not use it.
5. **`/api/dev/last-otp` can never be enabled with `prod`.** `DevOtpController`/`DevOtpRegistry` use `@Profile("(dev | test) & !prod")`, so `SPRING_PROFILES_ACTIVE=prod,dev` (or `prod,test`) does not expose codes.
6. **Production startup refuses public secrets** (`ProductionSafetyCheck`, active with `prod` or with no `dev`/`test` profile): `prod` combined with `dev` (whose defaults include a JWT secret, `dev-partner-key` and an admin password) fails, and so do the placeholders of `deploy/.env.example`, the dev defaults and the e2e values for `JWT_SECRET`, `PARTNER_API_KEY` and `ADMIN_BOOTSTRAP_PASSWORD` (they pass the length checks, so a forgotten placeholder meant forgeable admin tokens). A non-empty `PARTNER_API_KEY` needs at least 32 characters there (failed partner keys are not rate limited).
7. **A blocked company cannot fund milestones.** After a sanctions hit (APPROVED → BLOCKED) the company's active contracts remain, but `POST /api/client/milestones/{id}/checkout` now answers `409 COMPANY_NOT_APPROVED`, so no new money is taken from a sanctioned client. Stripe sessions created before the block are still honoured by the webhook (the money has already moved).
8. **A second fake checkout cannot become PAID.** Two checkouts of the same milestone could both be confirmed: the second was marked PAID (counted in GMV) without funding anything. Confirming it now answers `409 PAYMENT_ALREADY_PAID` and it stays PENDING. With Stripe, a second paid session is still recorded as PAID (real money) and logged for a manual refund.
9. **`null` list elements are validation errors.** `milestones: [null]` (project) and `prices: [null]` (application) caused a 500; they now return `VALIDATION_ERROR`.

Checked and found sound: ownership on every id-taking endpoint (projects, applications, CV, contracts, documents, milestones, messages, attachments, payments; foreign resources answer 404), role separation of `/api/admin/**`, `/api/partner/**`, `/api/engineer/**`, `/api/client/**`; CV only with `SHARE_FULL_CV` for that project and with a `FULL_CV` transfer event; pseudonymized profile and client views without email/CV/education/links/partnerRef; each party receives only the text of its own contract document (the code supersedes the "both documents" wording of backend item 7); engineer views without client price or company name (other than item 4); HS256 with algorithm pinning, `typ` separation, 32-char secret check, 7-day expiry, `jti` denylist and status checks on every request; SecureRandom 6-digit codes, HMAC storage, constant-time comparisons, atomic code consumption; bcrypt with a dummy hash for unknown admins, TOTP checked and counted as a failure; Stripe signature verification (with timestamp tolerance) and idempotent PENDING → PAID with a row lock, fake confirmation refused unless `PAYMENT_PROVIDER=fake`, amounts always taken from the contract milestone, `markFunded` only from `PENDING_FUNDING`; partner key constant-time, disabled when blank, request validation, a paid line can never be paid again (`409`); upload size limits, random storage keys, path checks in `LocalFileStorage`, sniffed content type, sanitized filename and `Content-Disposition: attachment` with `nosniff`; no SQL built from input, no entity bound from request bodies, `@Valid` on every body, page size capped at 100; no CORS configuration (same-origin behind nginx); client IP taken from `X-Forwarded-For` only through trusted internal proxies (`forward-headers-strategy: native`), so the rate limits cannot be bypassed as long as port 8080 is not published (it is not in `deploy/docker-compose.yml`).

Known and not changed: TOTP codes can be replayed within their 90-second window (no enrolment exists in phase 1; preventing it needs a stored last-used step); the Stripe webhook trusts the session amount (sessions are created server-side with a fixed price); `PAYMENT_PROVIDER=fake` and `MAIL_MODE=log` are still accepted under `prod` because the backend README documents running the prod image that way for tests, so production `.env` must keep `stripe`/`smtp`; anyone can lock an email's OTP login for 15 minutes with five wrong codes (inherent to the spec's lock); an approved engineer who withdraws `CROSS_BORDER_PROCESSING` or the declaration can still apply (product decision); contract views and chat in a later calendar year write no new `transfer_event` (treated as contract data, not profile disclosure); rate limits remain in memory (single instance).

## teams / reviews / totp

Phase 1.1 additions (design in `docs/SPEC.md` §12–§15). Migrations `V2__teams.sql`, `V3__reviews.sql`, `V4__admin_totp.sql`.

### Teams
1. **Module boundaries.** New module `team` owns `team` and `team_member`. The team snapshot of an application lives in `application_member` (module `project`) and that of a contract in `contract_member` (module `contract`). The team module asks "is this team (member) committed?" through `TeamWorkDirectory`, implemented by `ApplicationTeamWork` and `ContractTeamWork` with their own mappers only (same pattern as `AttachmentDirectory`, no bean cycle).
2. **The lead is the applicant.** A team application keeps `application.engineer_user_id` = lead and adds `team_id`; a team contract keeps `contract.engineer_user_id` = lead and adds `team_id`/`team_name`. The individual code paths, the unique keys and every existing response field keep working; team data is additive (`team`, `myAmountUsd`, …).
3. **Snapshot.** The application stores the active members and their split when the lead applies; the contract copies it at hire. Later changes to the team change neither. To keep the snapshot meaningful, leaving, removing a member and dissolving are refused with `TEAM_HAS_ACTIVE_WORK` while the team (member) is in an open application or a contract `PENDING_SIGNATURES`/`ACTIVE`.
4. **One application per engineer and project**, alone or in a team: enforced by UNIQUE(project_id, engineer_user_id) on `application_member` plus service checks in both directions (`ALREADY_APPLIED`, `data.aliases`).
5. **Consents and approval are checked when the lead applies** (and approval again at hire), like individual applications: withdrawing `SHARE_PROFILE_PSEUDONYMIZED` later stops new applications only. Errors that concern other members carry `data.aliases` so the h5 can name them.
6. **Transfers.** Every display of a team card writes one `transfer_event PSEUDONYMIZED_PROFILE` per member (list, shortlist, select, decline); a member's CV writes `FULL_CV` for that member only and needs that member's `SHARE_FULL_CV` for the project (`GET …/cv?alias=`).
7. **What the client sees** of a team: name, description, member aliases, roles and pseudonymized profiles; never the split. The team name/description are written by engineers for clients and are not keyword-flagged (projects are; teams have no free text beyond these two fields).
8. **What members see of each other:** alias, headline, skills, role, share and acceptance status. Never email, CV, education, links, partner reference or another member's agreement text (`documents` holds only the viewer's own agreement). Messages carry each engineer's own alias.
9. **Split rounding.** Member amount = talent × pct / 100 rounded **down** to the cent; the lead takes the remaining cents, so parts always add up to the milestone's talent amount. Shares have two decimals and must add up to exactly 100 (`SHARES_SUM_MISMATCH`).
10. **Documents.** `contract_document.engineer_user_id` (owner) was added and back-filled for existing engineer documents; the unique key is now (contract_id, kind, owner). `CLIENT_SERVICES` uses the unchanged template and names the professional as `QE-A, QE-B (team "Name")`. Members get `ENGINEER_DELIVERABLES_TEAM` (en/zh-CN, draft `2026-11-05`), stating the member's own share and amounts, that the team is not a legal entity, and that every member contracts and is paid separately. The contract is ACTIVE once every document (client + each member) is accepted; `engineerAcceptedAt` is the last member's acceptance.
11. **Delivery.** Only the lead submits milestones (`TEAM_LEAD_ONLY` 403 for members, a member knows the resource exists so no 404); any member can message and upload, and the lead may attach files uploaded by any member to a submission. Mails to "the engineer" go to every member.
12. **Money.** `settlement_line` is now unique per (milestone, engineer): one line per member with their own alias, partner reference and amount; `contract_milestone.settled_line_id` points to the first (lead's) line as the "settled" marker. Earnings show the viewer's own part (`talentAmountUsd` of `EarningView` is the member's amount; unchanged for individual contracts).
13. **Invitations** answer `ENGINEER_NOT_FOUND` for unknown, non-approved and disabled aliases alike (no probing). A team has at most 10 members (active + invited) and needs 2 active members to apply. Invitees can see the team they are invited to.
14. **Account deletion of a team member:** open applications that include them are withdrawn, contracts pending signatures that include them are terminated, teams they lead are dissolved and their other memberships end. An ACTIVE team contract blocks deletion, as for individual contracts.
15. `ConsentService.usersWithGrant(…, scopeRef = null)` now matches unscoped consents (it compared `scope_ref = NULL` before, which never matched; no existing caller passed null).
16. h5 fix found on the way: `contract.clientAgreementAccepted/Pending` were nested under `status.contract` in both locales, so the contract page showed the raw key; moved to `contract`.

### Reviews
17. Module `review` owns the `review` table; contract views get each side's review through `ContractReviews` (mapper-only implementation). One review per **side** (UNIQUE(contract_id, from_side)), not per user: in a team the lead reviews the client, and the client's review counts for every member's rating. `to_user_id` is the lead (client review) or the company's first member (engineer review).
18. Ratings are a running average stored with two decimals (reviews are immutable, so no recomputation across modules is needed). Texts are admin-only for now (`/admin/reviews`), including what clients wrote about engineers; engineers and clients see only their own side's review.

### Admin TOTP
19. Enrolment is two-step (pending secret confirmed by a code) so a mistyped scan never locks an admin out. The QR is drawn in the browser by the bundled `qrcode` npm package (data URL, allowed by the CSP `img-src data:`); the secret is also shown for manual entry.
20. Replay protection uses the last accepted time-step (`totp_last_step`), shared by login, enable and disable. A consequence: right after enabling, the next login needs the code of a later step (at most 30 s later).
21. Enrolment/disable errors are `TOTP_CODE_INVALID` **400** (not the login's `TOTP_INVALID` 401) because the web client logs out on any 401. A SUPERADMIN can reset another admin's TOTP; resetting one's own is possible but pointless.

### Stripe
22. `STRIPE_API_BASE` was added (SDK `RequestOptions.setBaseUrl`) because stripe-mock needs it; `ProductionSafetyCheck` refuses any value other than empty or `https://api.stripe.com` so the secret key can never be sent elsewhere in production. The stripe-mock image is pinned (`v0.197.0`) and it requires keys that look like `sk_test_<alphanumeric>`. The test also confirmed that the webhook verifies non-ASCII payloads (the body is read as UTF-8 for `application/json`) and that refunds go through `Session.retrieve` → `Refund.create(payment_intent)`.

## hardening

Production-readiness items (after the deployment kit). Migration `V5__admin_token_version.sql`. Tests: `AdminLifecycleIT`, `PartnerKeyRotationIT`, `HealthIT`, `AdminLifecycleGuardTest`, `PartnerKeyFilterTest`, `ContractPropertiesTest`, `ProductionSafetyCheckTest`, e2e `admin-lifecycle.spec.ts` and new checks in `deploy/test/run.sh`.

### Admin sessions and lifecycle
1. **Token version, not a denylist.** `admin_user.token_version` (INT, default 0) is copied into every admin JWT as claim `tv`; `AdminStatusPolicy` accepts an admin token only while the admin is `ACTIVE` **and** `tv` equals the column (one indexed `EXISTS` per request, the same query that already checked the status). Incrementing it ends every session of that admin at once. Rejected alternatives: a `jti` denylist needs the ids of tokens we never store; an issued-at cut-off has one-second resolution (JWT `iat`) and depends on clocks. Tokens issued before V5 have no claim and count as version 0, the column default, so the deploy signs nobody out.
2. **`POST /api/admin/me/password {currentPassword, newPassword}`** (any admin). Same policy as bootstrap/created admins: 12–200 characters, bcrypt. The new password must differ from the current one (`VALIDATION_ERROR`, `fields.newPassword = SAME_AS_CURRENT`). A wrong current password answers **`CURRENT_PASSWORD_INVALID` 400** (not 401: the back-office signs out on any 401), is audited (`ADMIN_PASSWORD_CHANGE_FAILED`, reason only) and does **not** count towards the login lockout (a hijacked session could otherwise lock the real admin out); instead the endpoint allows 5 attempts per admin per 15 minutes (`RATE_LIMITED`). Success increments the token version (all sessions end, the caller's included), clears a pending login lock, audits `ADMIN_PASSWORD_CHANGED` and returns `{token, admin}` like the login, so the browser that changed it stays signed in. TOTP is not asked again: the session was already opened with it.
3. **`POST /api/admin/admins/{id}/disable` and `/enable`** (SUPERADMIN) return the admin view. Refused for oneself (`CANNOT_DISABLE_SELF` 409) and for the last active SUPERADMIN (`LAST_SUPERADMIN` 409); unknown id 404. Both lock **every** `admin_user` row (`SELECT … ORDER BY id FOR UPDATE`, a small table) and re-check that the caller is still active (`ACCOUNT_DISABLED` otherwise), so two SUPERADMINs disabling each other at the same time are serialized: exactly one succeeds. Through the API the caller is always an active SUPERADMIN, so `LAST_SUPERADMIN` only triggers when the database moved on since the token was issued (roles edited by hand); it guards the invariant anyway. Disabling also increments the token version: open sessions fail on their next request (401) and are **not revived** by a later enable; login answers `ACCOUNT_DISABLED` 403. Enabling clears a login lock. Repeating either is a no-op without a new audit entry. Audit: `ADMIN_DISABLED` (email, roles), `ADMIN_ENABLED`. Admin roles still come from the token claims (they cannot be edited in phase 1).
4. **No password reset by another admin** and no e-mail recovery: an admin who forgot the password gets a new account from a SUPERADMIN (and the old one is disabled); `docs/OPERACIONES.md` 7.1 keeps an SQL fallback, which also increments `token_version`, only for "nobody can sign in".
5. **Back-office:** *My profile* has a password form (current, new, repeat; client-side checks for length, match and difference; `CURRENT_PASSWORD_INVALID` and field codes shown under the fields); on success the stored token is replaced by the returned one. *Administrators* shows a status tag and *Disable* (with confirmation) / *Re-enable*, never on the signed-in admin's own row. i18n es/en, ids in `web/TESTIDS.md`. The web also learned `ACCOUNT_DISABLED`, which the login already returned.

### Partner key rotation
6. **`PARTNER_API_KEY_PREVIOUS`** (optional): while set, `PartnerKeyFilter` accepts it next to `PARTNER_API_KEY`. Both comparisons are constant-time and always both run; the previous key never enables an API whose current key is blank. A request authenticated with it is logged at WARN and marked (request attribute); `AuditService` adds `partnerKey: "PREVIOUS"` and a `warning` to the detail of **every** `PARTNER` audit entry of that request, so future partner endpoints get it for free and the operator sees in *Compliance → Audit* whether the partner switched. The key itself is never logged.
7. **Production check:** when set, the previous key must be ≥ 32 characters, not a public example value, different from the current key, and the current key must be set.
8. **`deploy/rotate-secret.sh PARTNER_API_KEY`** now moves the current key into `PARTNER_API_KEY_PREVIOUS` (and records the start time in `/var/lib/qiao/partner-key-rotation`); a second rotation is refused until the first is finished. **`--finish-partner-rotation`** clears it, but first reads the audit log since the rotation started and refuses when the partner used the previous key after the new one (or never used the new one); `--force` overrides (leaked key). `status.sh` warns while a rotation is in progress.

### Contract party names in production
9. `ProductionSafetyCheck` refuses to start when `APP_CONTRACTS_HK_ENTITY_NAME` or `APP_CONTRACTS_PARTNER_ENTITY_NAME` (the `app.contracts.*` names of `ContractProperties`, printed in every contract template) is empty or contains `[`/`]` (the template placeholders and the `[dev]` defaults). **Exception: `PAYMENT_PROVIDER=fake`.** Such a run cannot take money and is already a test mode everywhere (the payment page says "test mode", `install.sh` and `status.sh` warn), so it starts with a `TEST MODE` warning and the contracts keep their visible `[…]` placeholders; switching to `stripe` without the names makes the backend refuse to start. This keeps the documented "install with fake for a smoke test" path working without a separate flag.
10. An empty variable (`APP_CONTRACTS_…=''` in `.env`) binds as an empty string, not as the default, so `ContractProperties` maps blank values to the placeholders. `install.sh` asks for both names (required with `stripe`, optional with `fake`; no brackets, quotes or backslashes, 3–200 characters; unattended: `QIAO_HK_ENTITY_NAME`, `QIAO_PARTNER_ENTITY_NAME`) and writes them to `.env`; for an existing `.env` it warns when they are missing with real payments. `deploy/.env.example` carries bracketed placeholders, so a copied example cannot reach production.

### Build version
11. `GET /api/health` → `{status, version, commit}`: `version` from `META-INF/build-info.properties` (`spring-boot-maven-plugin` `build-info` goal, i.e. the Maven project version), `commit` from `app.commit` = env `APP_COMMIT`, both `unknown` when absent. The backend Dockerfile declares `ARG/ENV APP_COMMIT` (last, so it does not invalidate the cached layers) and labels the image with it; CI passes `github.sha`, `update.sh` (build mode) and `install.sh` pass the full HEAD sha (`-mod` suffix with local changes) through the compose build arg `QIAO_BUILD_COMMIT`. `status.sh` prints both and warns when the commit does not match `QIAO_IMAGE_TAG`. The endpoint stays public: version and commit are not secrets for this deployment and the monitoring checks read the same endpoint.
